# Roadmap 0.4.0

Черновик списка задач на следующую версию. Основано на трёх источниках: аудит репозитория
(`sprints/2026-W48-refactoring/audit.md`), внутренний разбор конкурентов и замечания,
найденные при прогоне демо-сценария (`docs/DEMO-SCENARIO.md`).

В 0.4.0 входит и набор дефектов 0.3.0, который не выпускался отдельным хотфиксом:
`-o out\sub\file.json`, `--age-distribution` без `--age-range`, NPE в `--spec`,
`--unique-pool`, срок паспорта по рубежам, дубль паспорта в документах, `fill` без стектрейса.
Они уже в `CHANGELOG.md` → `[Unreleased] — 0.4.0`.

Принципы, которые не обсуждаются:

- `validum-core` остаётся **zero-dependency** — новая зависимость в ядро не заезжает.
- Изменения только аддитивные; ломающие — не раньше 1.0 (и тогда с переходным периодом).
- Каждая задача — карточка на доске + прогон тестов; «сделано» = зелёные тесты и обновлённые
  доки, а не «код написан».

## P0 — то, что видит пользователь

### 1. Регион в плоской выдаче адреса

Сейчас в CSV есть `registrationCity`, `registrationStreet`, `registrationPostalCode`,
но **субъекта нет вообще** — в `describe` видно «Казахстан, г. Алматы…», а по CSV не понять регион.
Для сверки с ЕСИА/анкетами и для отчётов это заметный пробел.

- Добавить `registrationRegion`, `postRegion`, `currentRegion` (и `regionType` следом) в
  `IndividualProfileFlattener`/`IpProfileFlattener`, русские метки — в `CsvExporter`.
- Аддитивно: колонки в конце блока адреса, старые имена не трогаем.
- Обновить golden-фикстуры (осознанно, один раз).
- Оценка: **0,5 дня**. Критерий: `coverage`/`describe` видят регион, golden обновлён, 860+ зелёных.

### 2. Формулировка в `coverage`

На испорченном наборе отчёт печатает «Согласованность: нарушений нет», хотя ИНН 10 из 10
невалидны. Формально верно (правила — про согласованность, не про валидность), но на демо и в
статье звучит как противоречие.

- Переименовать блок в «Согласованность полей» и добавить сводку «валидность ключевых полей:
  N из M невалидны».
- Оценка: **2 часа**. Критерий: `coverage bad.csv` показывает и согласованность, и валидность.

### 3. Узкий профиль выдачи (`--fields`)

64 колонки — это хорошо для засева БД и плохо для «покажите мне человека».
`--fields fullName,inn,age,region` + пресет `--fields short` (8–10 колонок).

- Работает в CLI (`generate … --fields`), в спецификации (`"fields": [...]`) и в REST
  (`?fields=`).
- Оценка: **1–2 дня**. Критерий: `--fields short` даёт понятную таблицу без потери ключей
  (`personId`, `inn`), `coverage` продолжает работать.

### 4. `--format xlsx` своим писателем

Настоящий Excel, ноль зависимостей: XLSX — это ZIP с пятью XML (`[Content_Types].xml`,
`_rels`, `xl/workbook.xml`, `xl/worksheets/sheet1.xml`, `xl/styles.xml`).

- Числа как числа, текстовые коды (`ИНН`, счёт, индекс) — как текст; ведущий ноль индекса
  сохраняется.
- Только в CLI (`validum-cli`), ядро не тянет `java.util.zip`-обвязку в публичный API — либо
  отдельный подпакет `ru.validum.core.export.xlsx` с явным javadoc «без зависимостей».
- Оценка: **2–3 дня**. Критерий: файл открывается в Excel/LibreOffice, `coverage --file *.xlsx`
  не обязателен (или читаем через тот же писатель).

### 5. CLI-JSON: флаги как boolean

CLI собирает JSON из плоской карты строк, поэтому `"terrorist": "true"` — строка, а в REST —
настоящий boolean. Для машинной обработки это ловушка.

- Вариант A (дешёвый): оставить как есть и задокументировать.
- Вариант B (правильный): `--format json` собирать через DTO (`IndividualProfileDto` уже есть в
  api — вынести в `core` или продублировать в CLI), плоскую карту оставить для CSV/SQL.
- Оценка: **1–2 дня** (B). Критерий: в JSON флаги boolean, имена полей совпадают с REST.

## P1 — рефакторинг (внутреннее, API не меняется)

### 6. `core/export` → три пакета

Сейчас в одном пакете кодеки (`CsvExporter`, `DocumentsCsv`), маппинг (`*Flattener`,
`ProfileFromCsv`, `CsvFiller`, `CsvImporter`) и доменные выгрузки ЦБ (`Ed807Exporter`,
`Ed808Exporter`).

- `ru.validum.core.format` — CSV/JSON/SQL кодеки;
- `ru.validum.core.mapping` — flatten/unflatten/fill;
- `ru.validum.core.cbr` — ЭД 807/808.
- Оценка: **2–3 дня**. Критерий: `git grep` старых импортов пуст, тесты зелёные, публичные
  классы сохранены как алиасы на один минор.

### 7. `DocumentsCsv` (435 строк) → три класса

Чтение, запись и склейка с профилем — по отдельности. Оценка: **1 день**.

### 8. `IndividualProfileGenerator` (728 строк) → `Builder` + коллабораторы ✅ (Builder вынесен)

Вынести `Builder`, настройку документов и адресов в отдельные классы; сам генератор оставить
сценарием. Оценка: **2 дня**. Критерий: золотые фикстуры не изменились (поведение то же).

### 9. `@Mixin` для общих опций CLI

`--seed`, `-n`, `-o`, `--format`, `--dialect`, `--table`, `--no-ddl`, `--region` дублируются
в 4 командах (24/18/15/9 опций). Общий `CommonOptions` + `@Mixin`. Оценка: **1 день**.
Критерий: `--help` не изменился по смыслу, тесты CLI зелёные.

### 10. README (1135 строк) → `docs/*`

`docs/quickstart.md`, `docs/cli.md`, `docs/api.md`, `docs/library.md`, `docs/data.md`;
README — витрина на 2–3 экрана со ссылками. Оценка: **1 день**.

### 11. `managers.txt` — 50 заглушек `ННН` ✅ (одна заглушка «Менеджер клиента»)

Персональный менеджер выводится как «ННН». Выбрать: реальные правдоподобные ФИО (по регионам)
или убрать поле из выдачи по умолчанию. Оценка: **0,5 дня**.

## P2 — возможности

### 12. Связанность набора (перенесено из 0.3.0)

`id` у профилей уже есть (`personId`), поэтому можно строить граф: `individual → accounts →
documents`, `organization → employees → individuals`, порядок вставки и `teardown.sql`.

- Оценка: **6–8 дней**. Критерий: `generate --spec` с `"relations"` создаёт согласованный набор,
  `fill`/`coverage` понимают связи, `teardown.sql` удаляет в обратном порядке.

### 13. Карты МИР

Тестовые PAN с ожидаемым исходом (как у ЮKassa), связка карта → банк → BIN.
Оценка: **3–4 дня**.

### 14. Условная генерация

`--where "region=77,gendern=MALE"` / `probe(seed=[...])` — набор под заданную выборку.
Оценка: **3–4 дня**.

### 15. Расширить отчёт `coverage`

Проверки ОКВЭД (код есть в классификаторе) и адресов (индекс ↔ регион), сейчас только
ИНН/СНИЛС/ОГРН/счёт. Оценка: **1 день**.
