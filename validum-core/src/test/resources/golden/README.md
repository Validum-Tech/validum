# Golden-фикстуры: контракт детерминизма

`individual.txt` и `organization.txt` — SHA-256 отпечатки каноничного набора профилей для
фиксированных `seed + asOf`. Это **публичный контракт**: если меняется генерация, меняется
отпечаток, и это видно в диффе — то есть изменение нельзя «протащить незаметно».

## Как это работает

`GoldenFixturesTest` для каждой пары `(seed, asOf)`:

1. генерирует профили (ФЛ — 3 записи, ЮЛ — 1),
2. собирает каноничный текст: одна строка на профиль, колонки через `\t`, без `personId`
   (он тоже детерминирован, но проверяется отдельно — `PersonIdsTest`),
3. считает SHA-256 и сравнивает с файлом.

Один файл — одна строка `<ключ> <хеш>`, где ключ — `individual:seed=42` и т.п.

## Когда фикстура «падает»

Красный `GoldenFixturesTest` означает: **изменились данные**, а не сломался тест.
Порядок действий:

1. Понять, что именно поменялось (дата выдачи документа? формат адреса? состав колонок?).
2. Если изменение намеренное и описано в CHANGELOG — обновить эталон:
   `./gradlew :validum-core:test --tests '*GoldenFixturesTest*' -Dvalidum.golden.update=true`
3. Закоммитить новый `golden/*.txt` **вместе** с изменением кода и строкой в CHANGELOG.

## Когда обновлять нельзя

- Если непонятно, почему отпечаток изменился, — это регрессия, а не «новая норма».
- Если меняется только порядок колонок в CSV — это не повод трогать golden, эталон строится из
  профилей, а не из вывода CSV.

## Чего здесь нет

Фикстуры фиксируют **детерминизм**, а не полную корректность: они не проверяют контрольные суммы
ИНН/СНИЛС/ОГРН (это делают `PropertyInvariantsTest` и `*ValidatorTest`) и не проверяют бизнес-правила
(это `ConsistencyTest` и тесты документов). Все три слоя нужны вместе.
